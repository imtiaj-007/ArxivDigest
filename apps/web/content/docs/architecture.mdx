## System overview

ArxivDigest is **two independently deployable subsystems sharing a single
Postgres database**:

<Mermaid chart={`flowchart TD
    cron[GitHub Actions cron<br/>daily 07:00 UTC]
    agent[apps/agent<br/>Python batch agent<br/>crawl • summarize • classify<br/>embed • rank • publish]
    db[(Supabase Postgres<br/>+ pgvector<br/>papers • digests • runs)]
    web[apps/web<br/>Next.js 16<br/>SSR/ISR + Fumadocs]
    vercel{{Vercel CDN}}
    langfuse[/Langfuse · LLM traces/]
    sentry[/Sentry · errors/]

    cron --> agent
    agent -- writes --> db
    agent -. POST /api/revalidate .-> web
    web -- reads --> db
    web --> vercel
    agent -.-> langfuse
    agent -.-> sentry

    classDef sub fill:#fafafa,stroke:#d4d4d8,color:#0a0a0a
    classDef side fill:#f4f4f5,stroke:#a1a1aa,color:#52525b,stroke-dasharray:4 2
    class agent,web sub
    class langfuse,sentry side
`} />

The two subsystems share **only the database schema** as their contract. The
agent never serves HTTP. The site never invokes the agent. They are
temporally decoupled — the agent writes, the site reads.

The cron does POST to the site's `/api/revalidate` endpoint after publish,
but that's a one-way cache-bust signal, not a request the site has to
honour for correctness.

## Why this shape

- **Agent as batch, not service** — daily cron pattern doesn't need an HTTP
  server; batch is simpler, cheaper, fewer attack surfaces
  (see [ADR-0001](/docs/adr/0001-pure-batch-architecture)).
- **Database as integration boundary** — both subsystems agree on schema;
  can evolve independently if the contract is preserved.
- **Site is mostly static or ISR** — pre-rendered or revalidated on demand;
  near-zero runtime cost.
- **GitHub Actions for orchestration** — free, observable, version-controlled.

### LangGraph stages

    class crawl,summarize,classify,embed,rank,publish stage
`} />

<Callout type="info" title="Resume checkpoint = DB status columns">
  Each stage is idempotent on its DB status column (`summary IS NULL`,
  `themes IS NULL`, `embedding IS NULL`, `score IS NULL`). Re-running the
  graph after a crash re-enters every node, but each only processes
  outstanding rows. **The DB status columns ARE the resume checkpoint** —
  see [ADR-0007](/docs/adr/0007-db-status-as-resume-checkpoint). Per-paper
  bulkhead: one failed call is logged and skipped, not fatal.
</Callout>

### Stage-by-stage detail

| Stage | Input | Output | Model / source | Failure handling |
|---|---|---|---|---|
| **crawl** | category list, limit | bare rows in `papers` | arxiv Atom API | UA + bounded 429 retry honoring `Retry-After`. `ON CONFLICT DO NOTHING` dedupes. |
| **summarize** | `papers WHERE summary IS NULL` | structured JSON in `papers.summary` | Llama 3.3 70B + instructor | `instructor max_retries=2`; tenacity backoff on Groq 429 (honors Retry-After); per-paper bulkhead. |
| **classify** | `papers WHERE themes IS NULL` | 1-3 slugs in `papers.themes` | Llama 3.1 8B Instant | Adapter post-filters to known taxonomy; falls back to `other` if empty; per-paper bulkhead. |
| **embed** | `papers WHERE embedding IS NULL` | `papers.embedding vector(1024)` | local `bge-large-en-v1.5` (CPU) | No external rate limits; pure compute. |
| **rank** | `papers WHERE score IS NULL AND embedding IS NOT NULL` | `papers.score` | pgvector novelty + Llama 3.1 8B impact | `blend_score(0.4 × novelty, 0.6 × impact)`; per-paper bulkhead. |
| **publish** | top-K by score | one row per UTC date in `digests` | template (count + leading themes + titles) | idempotent upsert by date. |

Per-model `AsyncLimiter` rate limiting (15 req/min on 70B, 25 req/min on 8B)
keeps successful runs comfortably under Groq's free-tier per-minute caps.

```sql
papers (
  id              uuid pk default gen_random_uuid(),
  arxiv_id        text unique not null,
  title           text not null,
  abstract        text not null,
  authors         text[] not null default '{}',
  categories      text[] not null default '{}',
  published_at    timestamptz not null,

  -- Generated fields (status columns — also the resume checkpoint)
  embedding       vector(1024),
  summary         text,             -- JSON-encoded PaperSummary
  themes          text[],
  score           real,

  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);

create unique index papers_arxiv_id_idx on papers (arxiv_id);
create index papers_published_at_idx on papers (published_at desc);
create index papers_embedding_idx on papers using hnsw (embedding vector_cosine_ops);
```

Full Drizzle schema at `packages/db/src/schema.ts`. Migrations in
`packages/db/drizzle/`.

### V1+ tables (not yet)

- `themes` (slug, name, description, display_order) — currently the
  taxonomy lives in code (`domain/themes.py` + `lib/themes.ts`) for V0
  velocity; will migrate to DB when it stops fitting in a file.
- `llm_audit` — per-call cost + latency + retries + cache hits. Useful
  when paid LLM is in play.
- `prompt_versions` — track active vs shadow prompts with `active_from` /
  `active_until` ranges (currently `VERSION` is a string constant in each
  prompt module).

### Row-Level Security (RLS)

The agent uses Supabase's service role (bypasses RLS); the web reads
through `postgres-js` against the transaction pooler with the connection
string. RLS policies on the `papers` and `digests` tables expose them
publicly to the anon role; `runs` is service-role only.

### Migrations

All migrations live in `packages/db/drizzle/` as Drizzle-generated SQL
files, checked into git. Both agent and site read from the same generated
schema; the agent's `asyncpg`-based `PostgresRepository` writes via raw
SQL embedded in `adapters/db/repository.py`.

## Data flow — typical day

<Mermaid chart={`sequenceDiagram
    participant GH as GH Actions cron
    participant A as Agent
    participant DB as Supabase
    participant W as Web (Vercel)
    participant E as Eval gate

    Note over GH: ~07:00 UTC (often delayed 1-3h)
    GH->>A: arxivdigest run --daily
    A->>DB: start_run (status=running)
    A->>A: crawl → 100 newest from arxiv
    A->>DB: upsert raw rows
    A->>A: summarize / classify / embed / rank
    A->>DB: write summary, themes, embedding, score
    A->>DB: publish — upsert digests row
    A->>DB: complete_run (per-stage counts)
    A->>W: POST /api/revalidate
    W->>W: bust ISR caches → /papers fresh
    GH->>E: arxivdigest eval --fail-on-regression
    E->>DB: read papers + classify ground truth
    E-->>GH: exit 0 (green) or 1 (red)
`} />

End-to-end: ~3-20 minutes depending on whether new papers arrived (Sun/Mon
are quiet; Tue-Fri are busy). Comfortably within GH Actions free-tier
budget.

## Per-paper lineage

The schema's status columns let us **regenerate any field** by nulling it:

- Re-summarize everything: `UPDATE papers SET summary = NULL`; the next
  cron's summarize stage picks them all up.
- Migrate embeddings to a new model (we did this for Voyage→BGE):
  `UPDATE papers SET embedding = NULL, score = NULL`; embed stage rebuilds
  in the new space; rank rebuilds scores on top.

V1+ when `papers.summary_prompt_version` exists, the migration becomes:
`UPDATE papers SET summary = NULL WHERE summary_prompt_version != 'summarize/v2'`
— smaller blast radius.

## Failure modes + recovery

| Failure | Detection | Recovery |
|---|---|---|
| **Groq down (5xx)** | HTTP error after tenacity retries | `MultiLLMClient` would route to Gemini if its key were set. Currently Gemini's free tier is exhausted; documented in [runbook](/docs/runbooks/groq-down). Wait it out. |
| **Groq rate-limit (429)** | tenacity catches; `aiolimiter` mostly prevents | Backoff respects `Retry-After`; if persistent, bulkhead skips the paper, the next cron retries (idempotent). |
| **arxiv index lag** | Crawl returns same IDs as yesterday → 0 new summarize rows | `DAILY_LIMIT=100` covers ~2 days of submissions, so weekend backlog still flows once arxiv re-indexes. Visible via `arxiv.fetched` log's `newest_id` / `oldest_published`. |
| **Supabase paused** | Connection error | Auto-resume on first request; one-time latency spike acceptable. Daily cron pings keep the project active. |
| **Single paper fails LLM call** | Exception inside stage | Per-paper bulkhead: catch, log, continue with remaining papers. The skipped paper stays `IS NULL` and gets retried next cron. |
| **Schema validation fail** | instructor catches Pydantic exception | Auto-retry with reformulated prompt up to 2x; on persistent fail, bulkhead skips. (Caught one deterministic 8B drift; fixed via [rank/v2 prompt](/docs/prompts).) |
| **Eval F1 drops below baseline** | Daily eval regression gate ([ADR-0008](/docs/adr/0008-daily-cron-eval-gate)) | Workflow goes red after publish; investigate; bump prompt version + re-eval. |
| **GH Actions runner crash mid-run** | `runs.status` stuck on `'running'` (no heartbeat yet — V1+) | Today: human notices. V1+: heartbeat workflow auto-marks stale runs as failed. |

## Scalability plan

Current scale is comfortable on free tiers. See
[free-tier headroom](/docs/stack#free-tier-headroom) on the Stack page.

| Volume | Papers/day | Action needed |
|---|---|---|
| **Current (V0)** | 50-150 | None |
| **V1 — covered subjects extended** | 200-300 | Bump `DAILY_LIMIT`, monitor 70B TPD |
| **V2 — extra LLM passes (critique, etc.)** | 500/day | Paid Groq tier; consider self-hosted vLLM |
| **V3 — multi-domain (full cs.*)** | 1500/day | Dedicated worker (Render / Railway $25/mo) — GH Actions cap becomes binding |
